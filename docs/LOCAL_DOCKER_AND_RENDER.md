# Local Docker and Render Deployment

## 1. Objectives

- One repository command starts the complete local platform.
- Use the supported SigNoz Foundry workflow.
- Run local services as Docker Compose containers.
- Deploy application and self-hosted SigNoz through Render Blueprint.
- Support SigNoz Cloud through environment changes.
- Expose `/`, `/api`, `/explorer`, and `/signoz`.

---

## 2. Local topology

Suggested ports:

```text
Gateway                8088
Web internal           3000
API internal           3001
Worker health internal 3002
PostgreSQL             5432
Redis                   6379
OTLP gRPC               4317
OTLP HTTP               4318
SigNoz UI direct        3301 or generated mapping
```

The gateway is the normal browser entry point.

---

## 3. Compose structure

```text
compose.yaml
infra/docker/compose.app.yaml
infra/signoz/generated/compose.yaml
infra/signoz/compose.override.yaml
```

The SigNoz file is generated by Foundry and is not edited manually.

---

## 4. Local startup

`./scripts/local-up.sh` should:

1. Check Docker and Compose v2.
2. Check Foundry.
3. Run Foundry gauge.
4. Run Foundry forge.
5. Validate merged Compose.
6. Start all containers.
7. Wait for PostgreSQL and Redis.
8. Run migrations.
9. Wait for SigNoz.
10. Validate Collector health.
11. Print URLs.
12. Optionally seed demo data.

User command:

```bash
make local-up
```

Conceptual merged start:

```bash
docker compose \
  -f compose.yaml \
  -f infra/signoz/generated/compose.yaml \
  -f infra/signoz/compose.override.yaml \
  up -d --build
```

Codex must adapt paths to actual Foundry output.

---

## 5. Shared network

Use a shared network such as:

```text
temporalguard
```

Application services must reach the Collector and SigNoz over the Docker
network. Use Foundry patches or an override.

---

## 6. Gateway

Default routes:

```text
/healthz       gateway health
/api/*         API
/explorer/*    web
/signoz        should be my self_hosted signoz view
/*             web
```

Preserve or strip `/api` consistently based on existing backend routing.

---

## 7. `/signoz`

Proxy mode is enabled only after tests prove:

- Assets.
- Client navigation.
- Authentication.
- API calls.
- Websockets/streams.
- Nested refresh.
- No prefix escape.

Fall back to redirect when unsupported.

---

## 8. Local modes

Self-hosted:

```text
SIGNOZ_MODE=self_hosted
```

Start with local SigNoz profile.

Cloud:

```text
SIGNOZ_MODE=cloud
```

Collector exports to Cloud and local SigNoz can be disabled.

Suggested Compose profiles:

```text
signoz-local
demo
```

---

## 9. Render strategy

Generate one final `render.yaml` from:

1. TemporalGuard application Blueprint.
2. SigNoz Foundry Render Blueprint.

The merge script must:

- Preserve names.
- Preserve disks.
- Preserve environment references.
- Preserve databases.
- Detect duplicate services.
- Detect duplicate ports.
- Fail on conflicts.
- Print a merge summary.

## 11. SigNoz on Render

Casting:

```yaml
apiVersion: v1alpha1
metadata:
  name: temporalguard-signoz
spec:
  deployment:
    flavor: blueprint
    platform: render
```

Generate:

```bash
foundryctl forge -f infra/signoz/casting.render.yaml
```

The generated Blueprint includes SigNoz, ClickHouse, Collector, migrator, and
required resources.

Do not hand-maintain a divergent copy.

## 12. Hosted routing

```text
https://app.example.com/

```

`/signoz` redirects to the public SigNoz service by default.

---

## 13. Hosted OTLP

Self-hosted mode:

- API/worker send to the Collector over Render private network.

Cloud mode:

- Collector sends to Cloud endpoint.

Do not expose the self-hosted OTLP receiver publicly unless TLS,
authentication, rate limits, and abuse protection are implemented.

---

## 14. Persistence

- Use Foundry-defined disks for SigNoz.
- Use managed PostgreSQL for application data.
- Do not horizontally scale a disk-bound service without supported storage
  architecture.
- Document retention and backup limitations.

---

## 15. Docker images

Use multi-stage production Dockerfiles.

Targets:

```text
web-production
api-production
worker-production
demo-production
```

Use non-root users where practical.

---

## 16. Migrations

- Exactly once per deployment.
- API and worker do not race.
- Migration failure blocks readiness.
- Backward-compatible changes.
- No TypeORM synchronize.
- Document rollback.

- Database URL.
- Redis URL.
- Auth secret.
- Encryption key.
- SigNoz API key.
- Cloud ingestion key.
- AI key.
- Existing Cloudinary secrets.
- Notification secrets.

---

## 22. Limitations to disclose

- Self-hosted SigNoz on Render has more operational overhead than Cloud.
- Path-prefix proxy support can vary with SigNoz versions.
- Resource sizes depend on ingestion volume.
- Local Compose is not a replacement for production orchestration.
